QA selection: [../qa-scope.md](../qa-scope.md). Player/build/release/deploy authorization: [../local-development.md](../local-development.md). These are the current gates; source/Editor finalization does not require a deployment.

Read project profile; never execute missing or guessed commands. Shared planning root is not the code worktree. Each implementation works on its owned branch/worktree and records ownership at start (session, branch, worktree, baseline main revision, process IDs and paths). Capture pre-existing status. Record exact spec revision used.

Use the integration lease for merge, canonical spec sync and deployment; use the planning lease for shared artifact edits/commits. Lock order is integration then planning; never reverse it. Release planning before long tests when safe. Do not wait for human responses holding either lease. No lease auto-stealing: confirm prior owner is stopped and inspect Git/deploy state before `lease recover` with a recorded reason.

Before merge refresh main, check unrelated changes, integrate only selected commits, resolve ordinary conflicts within scope and rerun affected checks. Synchronize selected spec deltas while preserving already integrated/newer requirements. Record a per-change spec-sync revision so archive does not reapply obsolete deltas. Check current release immediately before deploy; after deploy verify release identity and smoke at actual URL. Project profile must explicitly authorize this environment. No automatic production permission from this template.

Copy evidence/acceptance assets to a durable configured location and verify links before deleting worktree. Commit owned changes. Verify integrated commits are in main, worktree clean, resources belong to the task, and no active session uses them. Remove owned worktree and local branch with normal safe Git operations, no force deletion. Remote task branches are removed only when merged, owned, and not used by open reviews/other work. Unknown resources are reported, never swept. Stop owned dev servers only after verifying process identity.

Finalize from a stable checkout outside the worktree being removed. If the desktop task is attached to that worktree, use an available supported handoff or retain the owned cleanup debt at `finalizing` until no session uses it. Do not make creation of another task a prerequisite for recording acceptance. An independent later session can finalize existing resources; creating a new task still requires a user request. Remove temporary spec/config branches as well. Acceptance uses fresh worktrees for fixes, not retained implementation branches.

Each session startup/end checks inbox for finalization debt and its own dirty resources. Power loss may leave resources; retain ownership and stage so the next session can reconcile. `cleanup` evidence must include actual checks, branch/worktree removal, durable evidence paths and remaining foreign/active resources. Never assert whole-repository cleanliness while other workers legitimately have uncommitted work.

Human acceptance may be recorded before or after cleanup; neither substitutes for the other. Cleanup and metadata-only spec/evidence commits do not invalidate acceptance of the same result. Preserve the decision while finishing technical work, then use helper finalize. Archive only after all technical gates, valid human acceptance and resolved questions. Acquire planning lease, inspect latest canonical specs and the recorded sync evidence. If deltas already integrated, use supported archive skip-sync behavior only after verifying equivalence; otherwise sync safely. Run strict validation. Record archive location, commit archive changes and commit closure metadata; verify planning checkout clean. Metadata-only closure commits need not trigger app deployment. The archive record retains child/parent links, acceptance and release history.

## Star Tournament: post-acceptance cleanup and chat archive

Explicit acceptance authorizes routine cleanup and archiving of the completed task without another confirmation. Record it with `accept` first; complete existing technical gates, cleanup, `finalize` and OpenSpec archive. This also applies when acceptance arrives in a later chat: resolve the original chat IDs and owned paths from shared records and inspect their current state. Do not close a chat that still has active work, unresolved feedback or finalization debt. Archive the completed development/acceptance chats with the supported Codex `set_thread_archived` tool, after saving the final summary and durable links. This is separate from archiving the OpenSpec change. If a tool is unavailable, record the exact remaining debt instead of claiming completion.

Obsolete workspaces are task worktrees whose work is integrated, evidence is durable and no active task, Editor or Player uses them. Preserve the primary code checkout and shared planning home. Inspect fresh Git status, worktree inventory, task ownership and running processes. For a Codex-managed attached worktree prefer `archive_worktree`, verifying its snapshot and successful removal; needed ignored files must be preserved separately. For ordinary worktrees use safe Git removal and delete only merged, unused task branches. Never force-remove dirty/unmerged work or delete arbitrary workspace directories. Do cleanup from another stable checkout; an active attachment remains cleanup debt until it can be safely released. Use existing chats/tools; do not create a new chat without a user request.

Local build retention:

- Keep the current accepted application build for each platform/release channel, plus exact candidates still needed for pending/deferred acceptance, active QA, rework, install/update verification or a recorded rollback requirement. Preserve an explicitly requested historical build. Move retained builds out of a worktree before removing it and update durable links without changing their bytes or identity.
- Remove superseded accepted builds only when their relevant behavior is covered by a newer accepted build and no active change depends on the old artifact. Remove duplicates and temporary packaging/QA copies when their owner and replacement are verified. Age, filename or a newer unaccepted build alone does not prove obsolescence. Keep published/server artifacts and installed applications outside this local cleanup policy.
- Before deletion record each exact path, owner/change, platform, source revision, release/build identity, checksum and replacement/retention reason. Preserve acceptance decisions, manifests, checks, selected screenshots required by the render-retention policy below and useful logs in durable evidence; the full application binary need not be retained forever. Update references to identify a deliberately removed binary rather than leaving a misleading playable link.
- Check that no live Player, Editor/build process or other task uses the paths; never stop a foreign process. Delete only the verified obsolete build paths, then verify removal and that retained candidates still exist. Do not rebuild an old identity to disguise removal.

## Render retention after initiatives (user decision 2026-11-03)

- Keep bulk generated frames, render sweeps, rejected iterations and reproducible previews in ignored `.local/<initiative>/`. Do not commit whole render series to code or planning Git. Promote only the selected evidence needed for a decision, comparison, acceptance or reproducibility to shared planning, once, with source revision, capture settings and result links.
- At completion, cancellation or replacement of an initiative, review its render inventory as part of routine cleanup. Preserve editable originals, approved references, final representative before/after views, evidence of unresolved defects and original FAIL/NotRun, release/changelog images, and anything required by pending human/device acceptance or an active dependent task. Preserve a minimal sufficient set; neither age nor a newer image alone proves obsolescence.
- After verifying ownership, durable retained bytes and no active consumers, delete obsolete generated series and duplicate exports without another confirmation. Record paths, sizes, retention reasons/replacements and deliberately retired links in the initiative's cleanup evidence. Never delete the sole authored source or required irreproducible result. Uncertain or foreign files stay until their ownership and use are established.
- Untrack obsolete committed renders in a normal scoped commit and update their links, but report that this does not reclaim their historical Git objects. Routine completion does not authorize history rewriting, reflog expiration or aggressive pruning; compact existing Git history only under a separate explicit instruction. Prevent renewed growth by selecting evidence before its first commit.

Record worktree/branch/build removals and retained resources in `cleanup` evidence before finalizing. If a previously finalized change needs later housekeeping, append evidence/history while preserving its acceptance and lifecycle. At session startup/end inspect cleanup debt, including accepted/archived records with leftover resources; handle only verified inactive resources. After archiving other completed chats, archive the current chat last, when its full scope is finished. Report actual completion or exact blockers.

Before deletion, preserve authored code/assets/config/specs and durable evidence in the task Git (LFS when needed); a temporary archive/worktree must not be the only copy. If the project lacks Git, create or connect an appropriate source store. If commits are prohibited or technically blocked, retain files and record the blocker. Never delete the sole original asset or irreproducible result. After saving, remove only owned obsolete intermediate builds, backups, logs, exports, temporary directories and reproducible caches. Recheck Git including untracked/ignored files, processes and free space when material; report actual removals, retained artifacts/reasons and exact cleanup debt. Preserve active foreign work. Missing cleanup is not full completion.

## Unity process capacity

Use `~/.local/bin/unity-run --shared|--exclusive -- COMMAND`, not a project-local runtime lease or manual coordinator ACK. The wrapper admits up to four shared commands or one exclusive command across repositories. Shared is the default for autonomous Editor/Player checks, including UI fixtures. Exclusive is required only for performance measurements or shared desktop/focus/system input/audio-device QA; document the resource or metric before choosing it. Follow ../project-policy/unity.md. Do not hold planning/integration leases while waiting for Unity. Existing product coordination and Git leases remain independent.

## Source-only completion

Merged source/Editor work can finalize without a Player build or deployment using the structured delivery_scope contract in lifecycle.md. Keep deferred build/player/release/deploy gates explicit. A source-only accepted task is not a deployed release and does not unlock deployed dependencies. Copy retained evidence, preserve human decisions and perform the same ownership/cleanup checks. Historical profile channel flags describe capabilities or earlier operations; every new release/deploy needs its own explicit human command.
