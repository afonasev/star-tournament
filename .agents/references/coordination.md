# Ожидание координатора

Читай только при координации нескольких чатов или ожидании работы. Это правило поведения инструментов, не новый параметр `config.toml` и не разрешение создавать чаты, автоматизации или отправлять сообщения.

- Основной сигнал — событие завершения, требуемого действия или блокировки. Используй `wait_threads` для пользовательских чатов и `wait_agent` для разрешённых подагентов. У чатов промежуточный commentary не завершает ожидание; у подагентов доступна доставка сообщений/final.
- Для `wait_threads` явно ставь `timeoutMs: 120000` вместо короткого периодического опроса; передавай до 8 targets одним вызовом, `hostId` и последний `cursor` каждого как `afterCursor`. Возвращай модель к решению по новому событию. Длинный вызов запускай с асинхронным yield; не блокируй взаимодействие с пользователем дольше разрешённого текущими инструкциями.
- Таймаут без изменения не требует `read_thread`, нового запроса статуса исполнителю или повторения предыдущего решения. Сохрани курсоры и продолжи одно ожидание. Не совмещай постоянный опрос с мониторингом по расписанию.
- `read_thread` нужен для начальной передачи, нового blocker, смены этапа или просмотра итогового evidence. Выводи нужные поля/краткую сводку, не всю переписку. Не перечитывай неизменившийся результат.
- Не отправляй исполнителю «продолжи» или ACK/HOLDNEXT для имитации ожидания. Сообщение допустимо только при разрешённом изменении поручения или нужном новом решении. Авторизация на сообщения берётся от пользователя, а не от другой сессии.
- Неизменившийся несрочный мониторинг проверяется одним владельцем через 30–60 минут только в уже разрешённом расписании; новое расписание создаётся лишь по запросу пользователя.
- Перед интеграцией/поставкой и после содержательного события перечитай изменчивое Git/release/ownership состояние. Таймаут не означает остановку исполнителя.

## Длительные локальные процессы

- После первичной диагностики ожидай процесс 30–60 секунд либо до события завершения, соблюдая максимум API и лимит блокирующего вызова. Pending tool продолжай через поддерживаемый асинхронный yield/wait; не возвращай модель к решению по неизменившемуся выводу.
- Интервал 1–1000 мс допустим для конкретной диагностики или короткой интерактивной команды, с указанной причиной; это не default для компиляции, тестов, упаковки, импорта или admission. Для короткой команды не добавляй искусственное ожидание.
- Разделяй очередь/admission, startup/import, выполнение тестов и упаковку. Не опрашивай соседние чаты ради занятости Unity; runner ждёт ресурс. Planning/integration leases перед длительным ожиданием освобождай.
