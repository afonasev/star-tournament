# Delivery workflow

Читай при первом нетривиальном изменении, работе в worktree, интеграции или финализации; повторно — изменившийся или недостающий диапазон.

## Проверки

Действующий контракт выбора affected QA — [qa-scope.md](qa-scope.md); Player build и отдельные разрешения на поставку — [local-development.md](local-development.md). Tooling/docs без изменения Unity runtime проверяй без движка. Физические и performance gates без устройств/эталона остаются открытыми.

## Нетривиальные изменения

- Перед новой игровой механикой, оружием, картой, камерой, split-screen, управлением, UI-процессом, сетевой архитектурой, ботами, сохранением или аудио/графическим пайплайном сначала закрой продуктовые развилки и создай/обнови OpenSpec change.
- Сначала прочитай `docs/GAME_SPEC.md` и исследуй доступные факты. Спрашивай только о новых развилках либо конфликтах с утверждёнными решениями. Не реализуй, пока общее понимание не подтверждено.
- Интервью не нужно для опечатки, однозначной локальной правки стиля или ассета, маленького бага с единственным ожидаемым результатом, внутреннего рефакторинга, тестов, сборки и уже подробно утверждённого пункта спецификации.

## Handoff и Git

- Любые изменения — код, тесты, спецификации, документация, конфигурация и ассеты — выполняй в отдельном Git worktree на отдельной ветке. Основной checkout ветки `main` используй только для последовательной интеграции уже проверенных изменений; не редактируй файлы непосредственно в нём.
- Одна активная change/handoff-задача — один изолированный worktree и одна ветка. Перед созданием worktree обнови сведения о `main`, а перед интеграцией повторно проверь актуальные `git status`, ветку и список worktree, чтобы не затронуть параллельную работу.
- Канонический активный статус — shared OpenSpec change по [flow/lifecycle.md](flow/lifecycle.md). Handoff ссылается на change и содержит только точку продолжения по [context-efficiency.md](context-efficiency.md). Исторические `docs/tasks/` и ссылки на них сохраняй; параллельный статус, новые нумерованные handoff-документы и массовая миграция истории не требуются.
- Одна нетривиальная OpenSpec change или handoff-задача — одна задача Codex и один отдельный Git-коммит. Не смешивай посторонние изменения и не переходи к следующей фиче до проверки и коммита.
- Если нужно проверить конкретную ветку, запускай dev-стенд из worktree именно этой ветки. После запуска проверь доступность стенда HTTP-запросом и сообщи пользователю фактический URL с портом; не выдавай ожидаемый или ранее использованный адрес за подтверждённый.
- Интеграцию, разрешённую публикацию, spec sync, cleanup и archive выполняй по актуальным `.agents/references/flow/lifecycle.md` и `delivery.md` с shared planning home. Приёмку можно записать сразу или в другой сессии независимо от cleanup; technical accepted/archive требуют всех gates. Для каждого слияния обновляй состояние `main` и проверяй затронутые контракты; публикацию выполняй только в пределах project profile. Archive завершает принятый и технически финализированный change, а не предшествует его первой публикации.
- Исключение для коммита допустимо только по явному запрету пользователя или при технической невозможности; сообщай об этом явно.
