# Быстрая локальная разработка Unity

Решения пользователя 2026-10-08 и 2026-10-10 имеет приоритет над прежними QA/delivery references, профилями и историческими чеклистами.

- Параллельный Unity: `shared` по умолчанию для автономных проверок, включая UI/EditMode/PlayMode; `exclusive` только для замеров производительности или доступа к общему экрану, фокусу, системному вводу/аудиоустройству. До запуска читай `.agents/references/project-policy/unity.md`; название UI/Player само по себе не требует эксклюзивности.
- Обычный цикл: изменить исходники → проверить компиляцию и затронутые контракты → открыть правильную сцену в Editor и проверить её в Play Mode. Дистрибутив для этого не нужен. Запускай Editor из выбранного worktree через проектную обёртку; сохраняй правила владения процессами.
- До проверки кратко запиши изменённое поведение и общие зависимости. Для документации достаточно diff/ссылок; для tooling — контрактов и проверки маршрута без Unity, если поведение Unity не изменилось. Для локального UI — соответствующих UI/экранных тестов и Play Mode. Для локального gameplay — затронутых regression tests и сценария в Play Mode.
- UI/copy/layout, цвет, отступ, подпись, отображение значения и минорная локальная правка не запускают полный игровой набор, AI/physics stress и длинные natural matches. Выбери полный affected fixture и короткий сценарий изменённого поведения. Перенос UI по файлам, имя Runtime и сам commit/merge не являются причиной full.
- Общие зависимости и регрессия расширяют affected набор по фактическому влиянию. Полный прогон всех тестов требует отдельного явного подтверждения человека, даже при release/production/deploy. Неизвестное влияние сначала разбери; если без full нельзя проверить достаточно, объясни причину и запроси подтверждение. `CONFIRM_FULL_TESTS=1` фиксирует существующее разрешение, агент не выдаёт его себе. Длительные natural matches выбирай при влиянии на прогресс/исход/завершение матча или долгосрочное AI-поведение. Assertions/seeds/длительность/exact hashes сохраняются; пустые/skipped/missing XML и admission timeout остаются NotRun/неполной проверкой.
- Тесты и сборка разделены. `make check` — alias локального набора, а `make check-full` запускает полный набор без Player build только после отдельного подтверждения (`CONFIRM_FULL_TESTS=1`). `make check-local` — указанный в Makefile локальный набор, а не доказательство всей игры; добавляй проверки изменённого поведения. `make unity-editor` открывает Editor без сборки. `make build` отдельно собирает Player только по явной команде человека.
- Исключение: минимальная QA-сборка допустима в рамках фичи, только если конкретное затронутое поведение нельзя проверить иначе. Сначала объясни причину, затем выполни минимальную сборку и относящиеся проверки. Старый чеклист, удобство make/check/smoke или отсутствие wrapper не являются причиной. `make check-player` выполняет только явно заказанную Development-сборку; affected QA выбирается отдельно, полного прогона в её маршруте нет.
- Не собирай установщики/release/дистрибутивы и не публикуй, не загружай на сервер, не обновляй установленную игру без отдельной команды человека. Старые deploy_authorized и прежняя публикация не разрешают новую поставку. Разрешение собрать не разрешает выкатывать.
- Повторяй QA после относящейся к ней правки/ошибки; commit, merge и metadata-only changes сами по себе не требуют пересборки Player или повтора всего набора. После merge проверь затронутые контракты совместной версии, расширяй QA при новых зависимостях/конфликтах.
- Не пересоздавай worktree и не удаляй его Library между итерациями ради обычной проверки. Не копируй и не чисти чужие Libraries. Сначала используй сохранённые логи: admission, startup/import/compile, tests и build учитываются отдельно. Новые benchmark-сборки требуют команды человека.
- В финале перечисли выполненные проверки и оставшиеся Player/build/release/device/visual/audio gates. Editor/автотесты не закрывают самостоятельную платформенную или человеческую приёмку. Сохрани и закоммить исходную работу; остальные сборки и поставка ждут команды человека.

Тестовые wrappers задают отдельный `STAR_TOURNAMENT_QA_LAB_HISTORY` на запуск. Явный override сохраняется для проверки конкретной истории. Документация/tooling используют свои независимые проверки; `make check-tooling` не запускает Unity. См. [QA scope](qa-scope.md).
