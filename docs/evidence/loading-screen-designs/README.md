# Предварительный дизайн экранов загрузки

Дата: 10.10.2026. Основа: код main a1db27a7 и существующий `Resources/UI/menu-arena.png`.
Статус: пользователь выбрал вариант B (2). По замечаниям убраны «Подготовка главного меню» и нижние надписи «STAR TOURNAMENT» / «Подождите немного» на обоих экранах B. Unity runtime не изменён; выбор дизайна не является приёмкой работающей загрузки.

## Варианты

1. A — композиция главного меню. Название слева, орбитальная арена справа, компактный золотой индикатор внизу. Перед матчем добавлены выбранная карта и параметры из setup; короткая подсказка является предложением и может быть убрана.
2. B — центральная композиция. При старте звёздная эмблема с вращающимся кольцом; перед матчем центральная карточка со сводкой.

Для обоих экранов используется стиль «Арена / эфир»: MenuInk #101c29, MenuCard #1b2b3b, MenuGold #e7bb72. Новая эмблема B является концептом, не утверждённым логотипом.

## Предлагаемое поведение

- Показать загрузку до тяжёлой инициализации меню; убрать, когда меню готово к вводу.
- Показать второй экран сразу после действия начала матча; параметры брать из выбранного состава, режима и карты.
- Подготовка не должна блокировать отрисовку/индикатор. Нужны реальные границы этапов; одного yield перед синхронной работой недостаточно.
- Индикатор циклический, без процентов и искусственной задержки. Статус соответствует реальному текущему этапу.
- Начать матч автоматически после готовности мира, участников, камер и интерфейса; время матча не тратить на загрузку. Это предлагаемые критерии будущей реализации.
- Универсальная иллюстрация меню в концептах не является точным изображением выбранной карты. В реализации допустим общий фон без такого обещания либо настоящий preview выбранной карты.

Показанные 4 участника и 2000 очков — пример данных, не новые значения баланса.

## Исследованные точки

`ProvingGround.Start()` синхронно вызывает `InitializeDesignLab()`, создаёт арену и интерфейс. `CreateMatch(bool)` синхронно валидирует и фиксирует конфигурацию и состав, создаёт сессию и presentation. Причину длительности конкретного запуска/матча надо измерить при реализации.

В предыдущем расследовании 08.10.2026 зафиксирована длительная загрузка большой пользовательской DesignLabHistory. Это историческое свидетельство, текущая причина в этой задаче не проверялась. Пользовательскую историю нельзя удалять или сбрасывать ради устранения паузы.

Рекомендуемый маршрут после выбора дизайна: flow-standard, поскольку меняется startup/match lifecycle и нужна проверка отзывчивости. Не требуется создавать инициативу из двух самостоятельных фич: это один согласованный процесс загрузки.

## Артефакты и проверка

`index.html` — воспроизводимый дизайн-прототип, четыре последовательно расположенных экрана. Анимации индикатора поддерживают prefers-reduced-motion. `render.cjs` — генератор PNG через Playwright из доступного рабочего runtime. Пример:

```sh
NODE_PATH=<workspace-node-modules> <workspace-node> docs/evidence/loading-screen-designs/render.cjs
```

PNG: `a-start.png`, `a-match.png`, `b-start.png`, `b-match.png`. Проверены визуально после рендера в 1600×900; автоматическая проверка переполнения текста в 1280×720. Это проверка макетов, не Unity/runtime/physical acceptance. Unity, Player build и release не запускались.

Ветка с исходниками и PNG сохраняется для выбора и дальнейшей работы; временные сборки, кэши и логи этой задачей не создавались.
